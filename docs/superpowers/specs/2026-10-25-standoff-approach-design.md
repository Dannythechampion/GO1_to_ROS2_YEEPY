# 목표물 상대 접근 설계 — standoff 배치와 최종 접근

## 1. 목표

베이스를 대상물 앞 standoff 자세에 **거칠게** 배치하고, 마지막 구간을
대상물 상대 제어로 닫는다. 파지에 필요한 정밀도는 지도 정합이 아니라
**대상물 상대 정합**이 담당한다.

이 단계의 완료 범위는 다음과 같다.

- 대상물 자세에서 standoff 베이스 목표를 생성한다.
- Nav2 목표 완료 후 대상물 상대 오차를 닫는 최종 접근 단계를 둔다.
- 기존 안전 경로(`cmd_vel_safety_gate`)를 우회하지 않는다.
- 검출기는 교체 가능한 인터페이스로 두고, 구현은 범위 밖으로 한다.

팔 제어 자체, 검출기 구현, 움직이는 대상물은 이 설계의 범위 밖이다.

## 2. 왜 이 구조인가

2026-10-25 주행에서 베이스 정합만으로 파지 공차를 맞출 수 없다는 것이
측정으로 확인되었다. 복도에서는 축방향 병진이 관측되지 않아, 정합 자세와
스캔이 가리키는 자세의 차이가 2026-10-25 p95 0.214 m / 최대 0.340 m,
2026-09-18 양호 구간 p95 0.335 m / 최대 0.350 m까지 벌어진다. 이 퍼짐보다
좁은 도착 조건은 유지될 수 없어 로봇이 목표 주위를 왕복했다.

따라서 `xy_goal_tolerance`를 0.35 m로 두었다. 두 세션 모두 "오차만으로
도착 판정이 뒤집힐 수 있는 샘플"이 0.0% / 0.9%가 되는 값이다. 이 값은
팔의 작업 공차보다 크므로, **두 번째 루프가 반드시 필요하다**.

이는 이 분야의 표준 구성이기도 하다. 베이스를 멈추고 팔이 수행하는
stop-and-grasp가 기본값이고, 베이스 오차는 주행 거리에 따라 커지므로
시각 피드백으로 보정한다. 사족보행에 가장 가까운 선행 연구(QuadWBG)는
도달성 지표로 몸체 배치를 고르고 one-time grasp 정확도 89%를 보고한다.
Nav2 자체도 도킹 서버에서 같은 2단계를 쓴다: 내비게이션이 구역까지
데려다주고, 라이브 검출을 쓰는 제어 루프가 최종 정렬을 맡는다.

## 3. 현재 런타임 체인 (사실 확인된 값)

```
FAST-LIO            camera_init -> body
planar_base_frame   camera_init -> body_nav      (z=0, yaw만 유지)
slam_toolbox        map -> camera_init
Nav2 controller  -> /cmd_vel_nav
cmd_vel_safety_gate -> /cmd_vel                  (/localization_supervisor/ready,
                                                  ready_timeout 0.30, command_timeout 0.30)
go1_driver                                       holonomic: true, invert_lateral: false
                                                 max_linear_speed 0.20, max_yaw_speed 0.40
                                                 linear_deadband 0.025, yaw_deadband 0.04
```

`body_nav`가 Nav2의 `robot_base_frame`이고, 스택에 센서→베이스 정적 변환은
없다.

## 4. 단계 ① standoff 목표 생성

### 4.1 입력과 출력

| | |
|---|---|
| 입력 | `target_pose` (대상물, `map` 프레임), `standoff_distance` d, 선택적 `approach_yaw` |
| 출력 | 베이스 목표 자세 — 대상물에서 d만큼 떨어져 대상물을 향함 |

### 4.2 d를 무엇으로 정하나

팔은 **OpenMANIPULATOR-X**다. ROBOTIS URDF(`open_manipulator_x_arm.urdf.xacro`)의
관절 원점에서 링크 길이가 그대로 나온다.

| 구간 | URDF xyz | 길이 |
|---|---|---|
| joint2 → joint3 | `0.024 0 0.128` | 0.13023 m |
| joint3 → joint4 | `0.124 0 0` | 0.124 m |
| joint4 → end_effector | `0.126 0 0` | 0.126 m |
| **합(어깨 기준 최대 도달)** | | **0.38023 m** |
| joint1 → joint2 (어깨 높이) | `0 0 0.0595` | 0.0595 m |

합이 ROBOTIS 공표값 380 mm와 일치하므로 체인을 올바로 읽은 것이다.

완전 신전은 특이점이라 힘도 여유도 없으므로 실제 예산은 그 일부만 쓴다
(초기값 75% → 0.285 m). 대상물이 어깨보다 위/아래면 수평 도달은 더
줄어든다(구면 포락선).

**여기서 첫 초안의 제약식이 틀렸다.** "베이스 도착 오차 0.35 m를 흡수하고도
도달 가능"은 성립할 수 없다 — 0.35 m는 팔 전체 도달 거리 0.38 m에 육박해서
d가 음수가 된다. 팔이 실제로 마주하는 오차는 Nav2의 허용오차가 아니라
**최종 접근 단계가 보장하는 오차**다. 올바른 제약은 다음과 같다.

```
reach_budget   = horizontal_reach(대상물 높이 − 어깨 높이)
                 − approach_tolerance − grasp_margin
d              = arm_base_offset_x + reach_budget        (reach_budget > 0 이어야 함)
```

Nav2의 0.35 m가 만족해야 하는 조건은 따로 있고 훨씬 약하다 — **그 지점에서
대상물이 검출기 시야 안에 들어오기만 하면 된다.**

접근 단계 공차가 커질수록 d가 줄고, 어느 선을 넘으면 `reach_budget`이
음수가 되어 어떤 standoff도 불가능해진다. 그때는 접근 단계를 더 조이거나,
팔 장착 위치 또는 대상물 높이를 바꿔야 한다. 구현은 이 경우를 숫자로
반환하지 않고 거부한다.

### 4.3 접근 방향 선택

`approach_yaw`가 주어지지 않으면 후보 각도를 샘플링해 다음으로 점수화한다.

- costmap 자유 공간 (베이스가 설 수 있는가)
- 대상물 가시성 (검출기 시야가 가려지지 않는가)
- 도달성 (팔이 그 방향에서 닿는가)

선행 연구가 쓰는 reachability 기반 배치와 같은 구조다.

### 4.4 배치

새 노드 `approach_planner`로 둔다. `rviz_goal_bridge`는 지금의 게이트
역할을 유지하며 건드리지 않는다. standoff 목표는 기존 경로 그대로
`navigate_to_pose`로 보낸다 — 기존 중단/취소 규칙을 그대로 물려받기 위해서다.

## 5. 단계 ② 최종 접근

### 5.1 핵심 결정 — 회전하지 않는다

최종 접근은 **순수 병진(vx, vy)** 으로만 수행한다. 근거는 다음과 같다.

- Nav2의 stateful 래치가 이미 yaw를 `yaw_goal_tolerance` 0.15 rad 안으로
  맞춰 둔 상태에서 넘어온다.
- Go1 드라이버가 `holonomic: true`라 횡이동이 가능하다.
- 회전을 쓰지 않으면 `yaw_deadband` 0.04 rad/s 사각지대를 통째로 피한다.
  2026-09-18과 2026-10-25의 최종 정렬 실패가 모두 이 사각지대와 관련이 있다.
- 회전이 없으므로 progress checker와도 충돌하지 않는다.

`linear_deadband`는 0.025 m/s로 작아 제약이 되지 않는다. 0.35 m를
0.05 m/s로 닫으면 약 7초다.

### 5.2 제어

대상물 상대 오차를 0으로 만드는 비례 제어로 시작한다.

```
e      = target_in_body_nav - desired_offset
vx     = clamp(kp * e.x, -v_approach, +v_approach)
vy     = clamp(kp * e.y, -v_approach, +v_approach)
yaw    = 0
```

`v_approach`는 주행 속도보다 낮게 둔다(예: 0.08 m/s). 오차가 줄면
감속하되, **명령이 `linear_deadband` 아래로 내려가기 전에 정지 판정**한다.
이것이 yaw에서 일어난 사각지대의 병진판 재발을 막는 조건이다.

### 5.3 종료 조건

| 결과 | 조건 |
|---|---|
| `ARRIVED` | `|e| < approach_tolerance` 가 N주기 연속 유지 |
| `ABORTED:detection_lost` | 검출이 `detection_timeout` 이상 끊김 |
| `ABORTED:timeout` | 전체 접근이 `approach_timeout` 초과 |
| `ABORTED:override` | `/go1/manual_override` true |
| `ABORTED:fault` | `/go1/execution_fault` true |
| `ABORTED:localization` | `/localization_supervisor/ready` false |

`approach_tolerance`도 팔 제원에서 나온다.

### 5.4 안전

- 명령은 **반드시 `/cmd_vel_nav`로 발행**한다. `cmd_vel_safety_gate`를
  그대로 통과시켜 ready 게이트와 watchdog을 물려받는다. 게이트를 우회하는
  경로는 만들지 않는다.
- Nav2 목표가 **완료된 뒤에만** 동작한다. 따라서 `/cmd_vel_nav` 발행자가
  겹치지 않는다. 겹치면 두 제어기가 번갈아 명령하게 되므로, 이 순서가
  설계의 전제다.
- 중단 규칙은 `rviz_goal_bridge`와 동일하게 맞춘다.

### 5.4c 도크는 복도 양벽 마커 (2026-10-26 최종)

의자가 복도 한가운데 있고 양쪽에 벽이 있으므로, 테이프를 **등받이가 아니라
멈출 자리 양옆 벽**에 붙인다. 2026-10-26 실측이 네 가지 이유를 뒷받침한다.

| | 등받이 테이프 | **복도 양벽** |
|---|---|---|
| 가림 | 전방 = 팔·바구니 경로 | **측면, 섹터당 9,600~10,800점** |
| 고도각 | +0.3 m @ 0.35 m → **+40°** (FOV 상단 +52° 근처) | **≈ 0°** (FOV 한가운데) |
| 충돌 제약 | 도크가 피해야 할 물체 **뒤** → 밴드 0.035 m | **분리됨** — 멈출 위치가 설계 변수 |
| 복도 축방향 | 약함 | **강함** (이산 마커) |

마지막 항목이 특히 크다. 벽면 정합은 복도 축방향을 구속하지 못하고
(2026-10-25 주행이 헤맨 바로 그 퇴화), **이산 마커는 구속한다.**

마커는 로봇이 제자리에 섰을 때 **정횡(±90°)에 오도록** 붙인다. 그러면
두 마커의 **중점**이 곧 컨트롤러가 몰고 갈 목표가 되고, `approach_controller`는
**전혀 바꿀 필요가 없다** — 노드가 중점을 검출값으로, `stop_offset`을 목표로
넘기면 된다. 구현은 `corridor_dock.py`.

**yaw는 보고하되 베이스가 쓰지 않는다.** 여기서 회전하지 않는 것이 드라이버
yaw 데드밴드를 피하는 핵심이고, Nav2의 stateful 체커가 이미 방향을
`yaw_goal_tolerance` 안에 넣어 두었다. 남은 각은 **팔의 joint1이 흡수**한다 —
0.36 m에서 8.6°는 물체 위치로 0.054 m인데, 그건 팔이 지울 양이지 베이스가
지울 양이 아니다.

충돌 안전망도 바뀐다. 정면 도크용 `keep_out_distance`는 여기서 쓸 수 없다
(복도 마커의 중점은 로봇 근처에 있다). 대신 `forward_clearance()`가 **로봇 폭
채널 안의 최근접 반사**를 직접 재고, 코끝(0.32 m) + 여유 아래로 떨어지면
미션이 중단된다. 비어 있으면 `inf`를 돌려주어 장애물로 오인될 수 없다.

### 5.4a 도크는 재귀반사 테이프 2줄 (2026-10-26 결정)

의자 자체를 기하로 잡는 방식은 실측에서 품질이 나빴다. 로봇을 의자 앞에
세우고 측정하니 등받이가 **폭 0.595 m(기대 0.45), 직선 잔차 0.039 m,
높이 0.168 m**인 덩어리로 나왔다 — 좌석·다리·등받이가 한 클러스터로 섞인다.

Livox는 점마다 reflectivity를 주고, 같은 장면에서 측정한 분포는:

```
322,032점 중   reflectivity >= 150 : 1.42%
               reflectivity >= 180 : 0.018%  (57점)
               reflectivity >= 200 : 0.015%  (49점)
```

재귀반사 테이프는 255 근처로 포화하므로 **임계값 180이면 일반 재질과
경쟁하지 않는다.** 등받이에 **알려진 간격(0.30 m)으로 두 줄**을 붙이면 한
스캔에서 위치·방위·yaw가 모두 나오고, 간격 자체가 오탐 배제 조건이 된다.
구현은 `reflector_detector.py`.

라이다 프레임이 곧 `body_nav` 원점이므로 **외부 파라미터 캘리브레이션이
필요 없다.** 바닥 태그 + 배면 카메라도 유효한 대안이지만(정확도는 더
높다), SDK 설치·영상 경로·카메라 외부 파라미터·로봇 그림자 아래 조명이
모두 미지수다. 의자가 고정이라는 전제에서 둘 다 성립하며, 작업량으로
테이프를 먼저 택했다. 검출기는 `/approach/target_detection` 하나만 맞추면
교체 가능하다.

### 5.4b 충돌 제약 — 지금 조립으로는 여유가 거의 없다

테이프는 등받이에 있지만 의자의 **가장 가까운 부분은 좌석 앞단**이고, 이는
등받이보다 `seat_depth`(0.50 m)만큼 앞이다. 로봇 코는 라이다보다 0.32 m
앞이다. 따라서:

```
테이프 최소거리 = 로봇코(0.32) + 좌석깊이(0.50) + 여유
                = 0.82 m + 여유
```

반면 팔이 닿는 물체 최대거리는 **0.355 m**(라이다 기준)이다.

| 여유 | 테이프 최소 | 좌석앞단 물체 위치 | 팔이 닿나 |
|---|---|---|---|
| 0.00 m | 0.820 | 0.320 | O (코끝에 밀착) |
| 0.02 | 0.840 | 0.340 | O |
| **0.05** | 0.870 | 0.370 | **X** (0.015 초과) |
| 0.10 | 0.920 | 0.420 | X (0.065 초과) |

**팔이 로봇 코끝보다 3.5 cm밖에 더 나가지 못한다.** 팔 베이스가 라이다보다
0.15 m 앞인데 코는 0.32 m 앞이라, 38 cm 팔의 대부분을 자기 몸통 넘는 데
쓴다. 물체를 좌석 앞단에서 5 cm만 뒤로 두어도 닿지 않는다.

`dock_standoff()`는 이 경우 값을 반환하지 않고 **거부하며, 팔을 몇 m 앞으로
옮겨야 하는지 메시지에 넣는다.** 튜닝이 아니라 조립의 문제이기 때문이다.
팔을 **약 6.5 cm 앞으로** 옮기면 여유 5 cm + 물체 5 cm 뒤에서도 성립한다.

### 5.5 검출 인터페이스 (센서 비종속)

```
/approach/target_detection   geometry_msgs/PoseStamped
                             body_nav 또는 카메라 프레임, stamp 필수
```

검출기는 교체 가능하게 둔다 — 마커, 학습 기반 검출, 포인트클라우드 클러스터
어느 쪽이든 이 토픽만 맞추면 된다.

**MID-360은 근접 검출에 적합하지 않다.** FAST-LIO `preprocess.blind`가
0.5 m이고, 설령 낮추더라도 거치대와 팔 자체가 먼저 잡힌다. 최종 접근
검출은 카메라를 전제로 설계한다.

### 5.6 상태 보고

`/approach/status` (String, JSON)로 모든 전이를 낸다. 필드는
`rviz_goal_bridge`의 `/navigation/goal_status`와 같은 모양으로 맞추고,
RViz 마커도 `/navigation/goal_marker`와 같은 방식으로 띄운다. 조작자가
한 곳만 보면 되도록 하기 위해서다.

## 6. 상태 기계

```
IDLE
 └─ target 수신 ─> PLANNING ─ standoff 목표 산출 ─> NAVIGATING
                                                      │
                               Nav2 succeeded ────────┘
                                      │
                                      v
                                 APPROACHING ── 수렴 ──> ARRIVED ──> (팔에게 신호)
                                      │
   override / fault / LOST / timeout / 검출 상실 ──> ABORTED
```

`ARRIVED`에서 팔로 넘기는 신호가 이 설계의 출력이다. 팔이 무엇을 하는지는
범위 밖이다.

## 7. 확정된 값과 그 귀결

팔 장착 위치가 실측되어(2026-10-25 조립) 다음이 확정되었다.

```
팔 베이스 (body_nav)    x = +0.150 m,  z = -0.190 m    (라이다 기준)
어깨 높이 (body_nav)    z = -0.1305 m                  (= -0.190 + 0.0595)
최대 / 사용 도달        0.3802 / 0.2852 m              (75% 기준)
어깨 높이 대상물 standoff   0.355 m                    (approach_tolerance 0.05 기준)
```

### 7.0 계획된 시나리오 — 의자 위 물체

대상물은 의자 위에 두고, 선 자세의 Go1 상면보다 조금 위를 집는다. 라이다가
Go1 상면의 13 cm 구조물 위에 바로 올라가 있으므로, **Go1 상면보다 d 만큼 위**인
대상물은 `body_nav` 기준 `z = d − 0.13`에 있다.

| Go1 상면 대비 | `body_nav` z | 도달 | standoff |
|---|---|---|---|
| 0.00 m | −0.130 | O | 0.355 m |
| 0.05 | −0.080 | O | 0.351 |
| 0.10 | −0.030 | O | 0.337 |
| 0.13 | 0.000 | O | 0.324 |
| 0.20 | +0.070 | O | 0.273 |
| 0.25 | +0.120 | O | 0.206 |
| 0.30 | +0.170 | **X** | — |

**Go1 상면보다 약 0.25 m 위까지만 닿는다.** 그리고 대상물이 올라갈수록
standoff가 줄어든다 — 구면 포락선이 반경을 높이에 쓰기 때문이다. 0.25 m에서는
standoff가 0.206 m라 베이스가 상당히 가까이 붙어야 하고, Nav2 도착 오차가
0.35 m이므로 접근 단계가 그만큼 더 많이 이동해야 한다.

### 7.1 도달 가능 높이 — 바닥은 닿지 않는다

포락선이 어깨 중심 구면이므로, 어떤 standoff를 써도 닿지 않는 높이가 있다.

```
도달 가능 범위 (body_nav)   z = -0.4157 .. +0.1547 m
```

센서가 바닥 위 0.50~0.60 m에 있다고 보면 바닥은 `z = -0.50 ~ -0.60`이고,
**0.08~0.18 m 부족해 닿지 않는다.** 대상물은 테이블 등 높은 면에 있어야 하며,
바닥 물체를 집으려면 팔 장착을 낮추거나 Go1이 자세를 낮춰야 한다.
(센서의 바닥 대비 높이는 직접 측정된 값이 아니므로 범위로 적는다. MID-360은
하향 FOV가 -7°뿐이라 바닥을 거의 보지 못해 측정이 어려웠다.)

### 7.2 검출기 요구사항

standoff가 0.355 m인데 Nav2 도착 오차가 0.35 m이므로, 접근 단계 시작 시점에
대상물은 **전방 0 ~ 0.71 m 어디에나 있을 수 있다.** 검출기는 이 범위를
시야와 작동 거리 안에 담아야 한다. 이것이 Nav2 허용오차가 만족해야 하는
유일한 조건이다.

### 7.3 아직 미정

- 검출기 종류와 실제 시야 — `approach_tolerance` 0.05 m가 지켜지는지는
  검출기가 정해져야 확정된다.
- `usable_fraction` 0.75 — 로봇에서 검증되지 않은 초기값.
- `v_approach`, `kp` — 기본값은 있으나 실주행 미검증.

## 8. 검증 계획

- **단위 테스트**: standoff 자세 계산(거리·방향), 제어 법칙의 포화와
  데드밴드 상한, 상태 전이표, 모든 중단 경로.
- **로그 기반**: 기존 세션의 자세 기록으로 standoff 계산을 돌려
  베이스 도착 오차 0.35 m가 흡수되는지 확인한다.
- **실주행**: 팔 제원 확정 후. 이 설계는 주행으로 검증된 바 없다.

## 9. 시나리오 — 사전 기록된 좌표로 하나의 미션 (2026-10-26)

출발점과 도착점을 미리 `map` 좌표로 찍어 두고, 거기까지는 Nav2로 가고 그
다음 정합을 한다. 시나리오는 코드가 아니라 **데이터**로 둔다
(`config/chair_mission.yaml`):

```yaml
waypoints:
  start: {x: ..., y: ..., yaw: ...}
  chair: {x: ..., y: ..., yaw: ...}
sequence:
  - navigate: chair
  - dock
  - grasp
  - navigate: start
```

`chair`는 **Nav2가 멈출 자리**이지 로봇이 최종적으로 설 자리가 아니다. Nav2에는
`xy_goal_tolerance`(0.35 m) 안에 들어오고 벽 마커가 검출 범위에 들어오기만
요구한다. 나머지는 `dock` 단계가 닫는다.

`MissionRunner`가 두 컨트롤러 **위에** 앉는다. 둘 다 `/cmd_vel_nav`에
발행하므로 **동시에 활성화되면 안 되고, 그 보장이 러너의 역할**이다. 정리하면:

```
IDLE ─ start ─> NAVIGATING ─ Nav2 성공 ─> DOCKING ─ 수렴 ─> GRASPING ─> NAVIGATING ─> DONE
                     └────────────────── 실패/안전/검출상실 ──────────────> ABORTED
```

설계상 검증되는 것들:

- **`dock`은 `navigate` 바로 뒤에만 올 수 있다.** 도킹은 지도가 아니라
  검출값으로 움직이므로 마커가 범위 안에 있어야 한다. 미션 로드 시점에
  거부하는 편이 의자 옆에서 발견하는 것보다 낫다.
- **기록되지 않은 waypoint로 가는 단계는 거부된다.**
- 모든 중단은 사유를 들고 러너를 멈춘다. 실패한 단계를 조용히 지나가는
  미션이 로봇을 가구로 몰고 가는 방식이다.

`record_waypoint()`가 한 좌표만 교체해 파일을 다시 쓰므로, 의자나 마커가
움직이면 그 자리로 로봇을 몰고 가 자세를 캡처해 다시 기록하면 된다.

### 9.1 아직 비어 있는 것

- `chair_mission.yaml`의 좌표는 **자리표시자**다. 실제 기록 필요.
- 마커 간격 `strip_separation`은 복도 폭(기본 2.00 m, 허용 ±0.30) — 실측 필요.
- ROS 노드 배선(미션 로드, Nav2 액션, `/cmd_vel_nav` 발행, 팔 신호).
- 로봇에서 검증된 것은 **아무것도 없다.**

## 10. 출발점·도착점 테이프 미션 (2026-11-01)

9절의 시나리오에서 팔을 뺀 형태를 먼저 돌린다. **출발점과 도착점 모두**에
5.4c의 복도 양벽 마커를 붙이고, Nav2로 도착점까지 간 뒤 테이프에 정렬하고,
다시 출발점으로 돌아와 테이프에 정렬한다(`config/tape_mission.yaml`).

```yaml
sequence:
  - navigate: goal
  - dock
  - navigate: start
  - dock
```

### 10.1 테이프 모양 — 벽마다 세로 한 줄

한 지점에 **복도 양쪽 벽에 세로 스트립 한 줄씩, 서로 마주 보게** 붙인다.
라이다가 멈춰야 할 바로 옆(정횡)이다. 출발점 2줄, 도착점 2줄, 모두 4줄.

- **세로로 붙인다.** 복도 축방향으로는 폭(4~5 cm)만큼만 차지하므로 그
  방향의 중심이 날카롭다. 이것이 정확히 벽면 정합이 못 잡는 방향이다.
  가로 띠는 축방향으로 길게 퍼져 같은 일을 못 한다.
- **재귀반사(프리즘형) 테이프여야 한다.** 검출 임계값이 reflectivity 180이고,
  Livox는 일반 재질을 0~150, 재귀반사체를 151~255로 보고한다. 일반
  테이프·색 테이프는 벽과 구별되지 않는다.
- **폭은 테이프 한 폭(4~5 cm)이면 된다.** MID-360 사양(20만 점/s, 10 Hz,
  360°×59°에 고르게 퍼진다고 가정, 약 0.94점/deg²)으로 높이 밴드 안에 맺히는
  점 수를 어림하면, 노드가 0.2 s(2프레임)를 모으므로:

  | 벽까지 | 4 cm | 4.5 cm | 5 cm |
  |---|---|---|---|
  | 1.0 m | 73 | 82 | 92 |
  | 1.2 m | 51 | 57 | 64 |
  | 1.5 m | 33 | 37 | 41 |

  검출기 하한은 스트립당 20점이다. 의자 앞에서 벽까지 0.97~1.04 m였으니
  한 폭으로 충분하고, 벽이 1.4 m보다 멀면 두 폭을 나란히 붙인다(9~10 cm).
  실제 점 수는 `tape_waypoint check`가 잰다.

### 10.2 세로 길이 — 바닥에서 35~85 cm (50 cm)

검출기는 라이다 기준 높이 밴드 z −0.10..+0.20 m 안의 점만 센다. 스트립은
그 밴드가 벽에 닿는 범위를 덮어야 하고, Go1이 걸으며 몸이 기우는 만큼
(3° → 1 m 거리에서 ±5 cm) 여유를 더한다(`tape_span()`):

```
아래 끝 = H − 0.10 − 0.05 = H − 0.15
위  끝 = H + 0.20 + 0.05 = H + 0.25      (H = 라이다 바닥 높이)
```

H는 직접 잰 적이 없고 0.50~0.60 m로 추정된다. 두 끝을 모두 덮으려면
**바닥에서 35 cm부터 85 cm까지, 50 cm 길이**로 붙인다. 길게 붙여 생기는
밴드 밖 점은 걸러지므로 해가 없다 — 그래서 H를 모르는 문제는 밴드를 넓히지
않고 테이프를 길게 붙여 푼다. H를 줄자로 재면(MID-360 창 가운데까지)
`H−15 cm ~ H+25 cm`, 40 cm로 줄일 수 있다.

### 10.3 배치 규칙

- 두 줄은 **복도 축방향으로 같은 위치**에 마주 보게 붙인다. 어긋나면 yaw로
  보이고, 중점도 어긋남의 절반만큼 밀린다.
- 로봇은 두 줄의 **중점**에 라이다를 맞추므로 복도 폭의 가운데에 선다.
- 출발점과 도착점 쌍은 **3 m 이상** 떨어뜨린다. 검출 범위가 2 m이고 Nav2가
  0.35 m 안에 세우므로, 그보다 가까우면 4줄이 한꺼번에 보일 수 있다.
- 각 지점 반경 2 m 안에 다른 재귀반사체(안전 조끼, 비상구 표지 반사 스티커,
  소화기 스티커)가 없어야 한다. 검출기는 **정확히 두 줄**이 보일 때만 응답한다.

### 10.4 출발점·도착점 지정 — 지도 클릭이 아니라 테이프 앞에서 기록

지도에서 클릭하지 않는다. 로봇을 테이프 앞에 세우고 기록한다:

```bash
ros2 run omx_navigation tape_waypoint record start
ros2 run omx_navigation tape_waypoint record goal
```

이유:

- **오차가 상쇄된다.** 2026-10-25 주행에서 위치 추정은 복도 축방향으로
  0.2~0.34 m 어긋나 있었다. 지도 클릭은 실제 테이프 위치를 찍으므로 그 편향을
  그대로 싣고, 기록은 *위치 추정이 테이프가 있다고 믿는 곳*을 저장한다. Nav2도
  같은 위치 추정으로 움직이므로 편향이 같은 방향으로 들어가 상쇄된다.
- **로봇이 아니라 테이프를 기록한다.** 기록 시 로봇이 조금 비켜 서 있어도
  검출한 중점을 지도 좌표로 옮겨 저장하므로(`tape_pose()`), 저장값은 항상
  테이프 자리다. heading도 복도에 직각으로 맞춘 값이다.
- **복도 폭을 함께 잰다.** `marker_separation`에 실측 벽 간격을 저장하고,
  도킹 때 검출기를 그 값 ±0.10 m로 묶는다(기본값은 2.00 ± 0.30). 다른 지점의
  쌍을 잘못 잡을 여지가 줄어든다.

기록 파일은 설치 경로가 아니라 `$GO1_MISSION_FILE` 또는
`~/.ros/go1_tape_mission.yaml`에 둔다 — 배포 때마다 share 디렉터리가 다시
만들어지기 때문이다. 처음 기록할 때 패키지의 템플릿에서 복사한다.
`marker_separation`이 없는 지점(한 번도 테이프 앞에서 기록되지 않은 지점)이
있으면 미션은 시작을 거부한다.

덤으로, 출발점 테이프가 RViz의 2D Pose Estimate 클릭을 대신할 수 있다.
로봇을 기록할 때와 같은 방향으로 출발점에 세우고
`tape_waypoint init`을 실행하면 테이프로 계산한 자세를 `/initialpose`로
**한 번** 낸다. 쌍은 복도 양 끝에서 똑같이 보이므로 방향은 기록 때 방향을
가정한다.

### 10.5 노드 배선 — 기존 게이트를 그대로 지난다

`tape_mission` 노드가 `MissionRunner`를 ROS에 잇는다.

- **목표는 `/goal_pose`로 `rviz_goal_bridge`에 낸다.** 브리지가 Nav2로 가는
  유일한 길이라는 원칙(그리고 READY·리모컨·명령 미실행 게이트)을 그대로
  쓴다. 결과는 `/navigation/goal_status`에서 좌표로 맞춰 읽는다. IGNORED,
  REJECTED, PREEMPTED, CANCELED, ABORTED는 모두 실패다. 3초 안에 브리지가
  목표를 인지하지 않으면 중단한다.
- **도킹 명령은 `/cmd_vel_nav`로** 내므로 `cmd_vel_safety_gate`가 READY로
  거른다. Nav2 성공 직후 1.5 s는 내지 않는다 — velocity smoother가
  `velocity_timeout`(0.35 s)이 지난 뒤 0까지 감속하며 같은 토픽에 계속 내기
  때문이다.
- **점군은 `/livox/lidar`(CustomMsg) 원본**을 0.2 s씩 모아 쓴다. 매 프레임
  반사 점과 로봇 폭 채널만 남겨 Python 루프를 줄인다.
- **안전망.** 앞·뒤 채널(로봇 몸 안쪽 점은 무시: 코 0.32, 꼬리 0.33)에
  0.10 m 안으로 무엇이 들어오면 중단. 검출 중점이 정지 위치에서 0.60 m보다
  멀면(`max_correction`) 기록된 쌍이 아니라고 보고 몰지 않고 중단 — Nav2가
  0.35 m 안에 세우므로 그보다 먼 쌍은 다른 것이다.
- 시작·취소는 `/mission/start`, `/mission/cancel`(std_srvs/Trigger), 진행은
  `/mission/status`(JSON). 취소 시 Nav2 목표는 빈 CancelGoal(전체 취소)로
  끊는다 — 목표 핸들은 브리지가 가지고 있기 때문이다.

### 10.6 아직 검증되지 않은 것

- 점 수 표는 사양으로 어림한 값이다. 실제는 `tape_waypoint check`로 잰다.
- 라이다 바닥 높이 H(0.50~0.60 m 추정).
- 실제 복도 폭과 테이프 간격 — 기록 때 측정된다.
- Go1이 0.08 m/s 이하의 옆걸음(vy)을 데드밴드 밖에서 실제로 따르는지.
- 로봇에서 주행한 적은 **없다.**

### 10.7 현장 실측 (2026-11-01, 출발점, 라이다 유닛 .135)

- 테이프 반사도 중앙값 **150~164, 최대 175**, 바로 옆 벽 **20~34**. "테이프는 255 근처로
  포화"라는 5.4a의 가정은 이 테이프·유닛에서 틀렸다. 임계값 180이면 아무것도 안 보이고,
  복도 마커 임계값을 **120**으로 낮췄다. 120에서 테이프 점은 프레임당 약 109개(99% 유지),
  2 m 안의 비테이프 점은 약 3개라 스트립당 최소 20점에 한참 못 미친다.
- 검출은 0.2 s 창 10/10, 중점 x −0.040 m가 ±1 mm로 안정, 벽 간격 2.028 m.
